1. The Problem: Playing "Twenty Questions" With a Broken Mouse

Imagine your car’s "Check Engine" light turns on. You call the mechanic, and instead of plugging a diagnostic scanner into your dashboard, an automated voice asks you: "Have you tried turning the ignition off and on again? Does the engine sound more like a 'clunk' or a 'whir'?"

For the last decade, that’s how hardware customer support (CX) has worked. When a user’s wireless mouse stutters or its battery drains overnight, cloud chatbots spend 25 minutes asking the user to guess what’s wrong. Half the time, frustrated users give up and request a warranty replacement (RMA) for a device that isn't even physically broken—it just has a receiver plugged too close to an unshielded USB 3.0 cable or a stuck NVRAM sleep state!

The OBD-II Scanner Analogy

Modern peripherals (like the Logitech MX Master 3S) already have an internal "flight recorder" speaking a protocol called HID++ 2.0. It knows its exact signal-to-noise ratio in decibels, its Li-Po battery voltage down to the millivolt, and its internal cell impedance. Our prototype acts like a mechanic's OBD-II scanner built right into a webpage—plugging directly into the mouse via WebHID and using Chrome’s local on-device AI to translate raw hexadecimal bytes into a 1-click fix.

2. Technical Architecture: How the Pieces Talk

Normally, AI web apps send data across the internet to a giant cloud server. But corporate IT departments and privacy laws (GDPR/CCPA) hate sending raw hardware serial numbers and system telemetry to third-party clouds. Our architecture flips the script: 100% of the work happens inside the user's browser tab.

1. Hardware Layer Physical USB/BLE Device OR Simulator emits 20-byte HID++ report
➜
2. Binary Decoder webhidService.ts unpacks Big-Endian millivolts, RSSI, & bitmasks
➜
3. On-Device AI chromeAiService.ts prompts local Gemini Nano or Heuristic Fallback
➜
4. 1-Click Fix sendReport() writes remediation bytes back to the device

Decoding a 20-Byte HID++ 2.0 Packet

When the mouse sends a report, it doesn't send English text. It sends 20 raw bytes of hexadecimal numbers like this: 

11  FF  18  0F 3C  18  56  09  03  03 E8  24  24  00 00 00 00 00 00 00
│   │   │   └──┬─┘ │   │   │   │   └──┬─┘ │   └── Byte 11: FW Build (0x24 = B0036)
│   │   │      │   │   │   │   │      │   └────── Byte 10: USB 3.0 Noise (0x24 = 36 dB)
│   │   │      │   │   │   │   │      └────────── Bytes 8-9: Polling Rate (0x03E8 = 1000Hz)
│   │   │      │   │   │   │   └───────────────── Byte 7: Fault Bitmask (0x03 = Noise + Retransmit)
│   │   │      │   │   │   └───────────────────── Byte 6: Cell Impedance (9 = 0.09 Ω)
│   │   │      │   │   └───────────────────────── Byte 5: |RSSI| (0x56 = -86 dBm)
│   │   │      │   └───────────────────────────── Byte 4: Packet Drop Rate (0x18 = 24%)
│   │   │      └───────────────────────────────── Bytes 2-3: Battery mV (0x0F3C = 3900 mV)
│   │   └──────────────────────────────────────── Byte 1: HID++ Feature (0x18 = RF Quality)
│   └──────────────────────────────────────────── Byte 0: Device Slot (0xFF = Direct/Receiver)
└──────────────────────────────────────────────── Report ID (0x11 = 20-byte Long HID++ Report)

3. Tour of the Codebase: Where Everything Lives

We organized the codebase with strict separation of concerns—meaning UI components never do raw binary math, and hardware services never worry about CSS colors:

src/types/ — The Contracts

Contains webhid.ts, diagnostics.ts, and privacy.ts. Think of this folder as the architectural blueprints. Before writing a single function, we defined the exact shape of a telemetry frame, an AI diagnosis, and a privacy audit record.

src/services/webhidService.ts — The Binary Translator

Talks to Chrome’s navigator.hid API, converts raw DataView byte buffers into human-readable hex strings, unpacks 16-bit Big-Endian integers, and decodes bitmask flags.

src/services/simulatorService.ts — The Flight Simulator

Generates authentic 20-byte HID++ fault packets for RF interference, Li-Po battery sag, and firmware NVRAM corruption—and mutates those registers when a user clicks a 1-click fix.

src/services/chromeAiService.ts — The Local Brain

Detects Chrome’s built-in window.ai.languageModel (Gemini Nano), feeds it a Senior Hardware Engineer system prompt, sanitizes its JSON output, and provides a deterministic local fallback engine.

src/services/privacyAuditService.ts — The Security Guard

Hashes every piece of hardware telemetry locally (sha256:local:...) and proves that 0 bytes were transmitted to external servers.

src/components/ — The 4-Step Cockpit

Modular React components guiding the user through Step 1 (Connect/Select Profile), Step 2 (Live Hex & Registers), Step 3 (AI Root Cause), and Step 4 (One-Click Remediation).

4. Key Technical Decisions & Tradeoffs

Decision A: Dual-Mode Hardware Ingestion (Real WebHID + Built-In Simulator)

Why? Operating systems (Windows and macOS) lock standard mouse/keyboard HID collections so malicious websites can’t keylog you. Only vendor-specific HID collections (Usage Page 0xFF00) can be opened by WebHID. Furthermore, an executive reviewing this prototype might be on a laptop trackpad without a broken Logitech mouse plugged in! By feeding both real WebHID events and simulated HID++ packets into the exact same binary parser (parseHidReportToFrame), we get 100% real-world fidelity AND instant 1-click demoability.

Decision B: Resilient Local-First AI (Gemini Nano + Heuristic Fallback)

Why? Chrome’s window.ai Prompt API is revolutionary, but it currently requires enabling experimental chrome://flags and downloading a local model. If our app crashed or showed a blank screen when window.ai wasn't enabled, 90% of testers would hit a brick wall. Instead, we built a Bilingual Engine: it uses window.ai.languageModel whenever present, and seamlessly falls back to a deterministic on-device hardware rule engine when absent.

The Escalator Analogy

Comedian Mitch Hedberg once joked: "An escalator can never break: it can only become stairs." That is how good engineers build AI features. If the on-device neural network (window.ai) isn't available yet on a user's machine, the app doesn't break—it gracefully becomes a deterministic diagnostic expert system.

Decision C: Zero-Leak Support Bot Handoff via window.postMessage

Why? How does a cloud support chatbot (like Zendesk or Intercom) know that the customer's mouse was fixed locally without violating our Zero-Leak privacy guarantee? We built supportBotBridge.ts and the interactive SupportBotDrawer.tsx sandbox: when the local scan or 1-click fix finishes, the browser emits a sanitized CX_HARDWARE_DIAGNOSIS_RESULT event via window.postMessage containing the ticket status (RESOLVED_RMA_DEFLECTED) and the local SHA-256 compliance certificate ID—while keeping externalBytesSent: 0.

5. Real Bugs & Gotchas We Solved Along the Way

Every engineering project hits sharp edges where theory meets reality. Here are three real issues we encountered and how we fixed them:

Bug #1: The "+1 Byte Offset Shift" in Custom Hex Strings

The Trap: When WebHID fires an inputreport event in the browser, it strips the 1-byte Report ID (0x11) into event.reportId and puts the remaining 19 bytes into event.data. However, when a hardware engineer copies a 20-byte hex string from a USB packet sniffer (11 FF 18 0F 3C...), byte 0 is the Report ID! If you naively pass all 20 bytes into the payload buffer, every byte index shifts right by 1—turning the Battery Voltage bytes into Packet Drop Rate!

The Fix: In parseCustomHexStringToFrame(), we added smart header inspection: if the first byte is a known HID++ Report ID (0x10, 0x11, or 0x12), we extract it as reportId and slice the remaining bytes into the payload DataView.

Bug #2: Small LLMs Love Wrapping JSON in Markdown Backticks

The Trap: Even when you tell an on-device LLM like Gemini Nano "Output ONLY valid JSON", it frequently replies with ```json { "conditionTitle": "..." } ```. Passing that string directly to JSON.parse() throws a fatal SyntaxError.

The Fix: We wrote extractJsonFromModelOutput() in chromeAiService.ts, which strips Markdown fences via regex and extracts the substring between the first { and last } before parsing.

Bug #3: Vite vs. Vitest TypeScript Config Collision

The Trap: Adding a test: { environment: 'jsdom' } block inside vite.config.ts works when running tests, but fails during npm run build (tsc) if defineConfig is imported from 'vite' instead of 'vitest/config'.

The Fix: Switching line 1 of vite.config.ts to import { defineConfig } from 'vitest/config'; unified the TypeScript types for both Vite builds and Vitest test runs.

6. Lessons Learned: How Senior Engineers Think & Work

  • 1. Test the Binary Boundaries First: UI bugs are obvious; bitwise shifting bugs ((b2 << 8) | b3) are silent killers. Writing fast unit tests for hex-to-byte conversion and bitmask decoding in Phase 3 meant Phase 4 (building the UI) went smoothly without a single data-corruption bug.
  • 2. Prove Security Claims With Telemetry, Not Marketing Copy: Anyone can put a "100% Private" badge on a website. Building the Zero-Leak Compliance Ledger that hashes each local operation and lets enterprise IT admins export a JSON certificate turns a marketing claim into verifiable engineering proof.
  • 3. Design for Compound Failures: Real hardware rarely fails in a neat textbook way. When a mouse is near a noisy USB 3.0 port, it retransmits packets 5x more often, which spikes current draw and causes an aging battery to sag! Because our diagnostic engine evaluates bitmasks composably rather than with mutually exclusive if/else blocks, it automatically detects and explains Compound Faults when you inject a multi-fault hex string.
